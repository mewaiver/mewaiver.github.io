The checkout API is slower, but its error rate has barely moved. Authentication looks healthy. Database utilization is ordinary. A trace points toward an inventory partner, yet the partner reports no comparable rise in processing time. The team has metrics, logs, and traces; it still cannot say where the delay began. This is a hypothetical incident, but the uncertainty is familiar: each instrument measures a boundary, and the decisive wait may fall between boundaries.

Distributed systems make this problem more acute because one customer action crosses processes with different clocks, queues, owners, and failure policies. A gateway's response time includes work it cannot inspect directly. A successful order may have required a retry that concealed a failed first attempt. Even when two services agree on a request identifier, neither necessarily records the time spent waiting for a connection, scheduling a task, or receiving a reply. The investigation therefore has to reconstruct both the observed path and the places where evidence is absent.

## Detection is the start of diagnosis

Monitoring answers questions a team prepared to ask: which route is slow, how many requests fail, and whether a resource is saturated. Observability supports questions that arise only after those symptoms appear. The distinction is operational, not a claim that monitoring and observability are separate products. Google's [SRE guidance on monitoring distributed systems](https://sre.google/sre-book/monitoring-distributed-systems/) separates user-visible symptoms from possible causes and explains why internal measurements matter for debugging. A dashboard can show that order latency rose; it cannot establish whether the order service waited on its own connection pool or on the partner behind that pool.

The first useful comparison is across populations of requests. Did the latency distribution change for every route, only `POST /orders`, only one region, or only requests that reserve inventory? Did traffic, deployments, retries, and timeouts change at the same time? Metrics can answer those aggregate questions efficiently. Their limitation is built into the aggregation: a histogram may show a long tail without preserving the sequence of calls behind any one slow order. Averages are especially weak here, because many fast requests can hide a small but consequential slow group.

Logs preserve local decisions that aggregates lose: a timeout, a retry reason, a connection-pool rejection, or the version of a dependency selected for a request. They are strongest when events are structured and include a request or trace identifier. They are weaker when timestamps are the only join key; concurrent requests can generate nearly identical messages. Distributed traces provide the missing request-level structure, but only for operations that were instrumented, propagated, retained, and successfully exported. The three signals complement one another because they answer different questions, not because their combination guarantees a complete account.

## The trace is a map of recorded operations

A trace groups spans for a logical operation. Each span records an operation's start and end, its own span ID, a shared trace ID, and, when applicable, its parent span ID. The parent relationship lets an investigator follow a gateway request into an order-service call and then into a database query or partner request. Span attributes and events can add route, outcome, or retry details. The [OpenTelemetry trace data model](https://opentelemetry.io/docs/specs/otel/trace/data-model/) defines these relationships and also allows links for causal connections that do not fit a single parent-child tree, such as some asynchronous workflows.

Those relationships depend on context propagation. An HTTP client injects trace context into an outgoing request; the server extracts it before creating its span. The W3C [Trace Context specification](https://www.w3.org/TR/trace-context/) standardizes the `traceparent` header used for this exchange. The same principle applies to message metadata and background jobs, where context must survive a queue handoff. If a gateway creates one trace but a message consumer starts another without carrying or linking context, the backend may show two plausible fragments instead of one end-to-end execution. A shared timestamp cannot repair the missing causal relationship.

Propagation and recording are different operations. A service may forward trace context while its own span is not recorded because of sampling; conversely, it may record a local span while failing to pass context downstream. Export can also fail after the request completes. An absent child span is therefore ambiguous: the code may never have called the dependency, the call may be uninstrumented, context may be broken, the span may have been dropped, or the query may cover only part of the trace. An investigator should test these possibilities before treating the visible trace as the whole request.

Span duration is likewise evidence about an interval, not an explanation for it. A client span around a partner call can include connection acquisition, network transfer, remote processing, timeout, and backoff, depending on where the instrumentation starts and stops. Parent and child spans may overlap; adding their durations double-counts time. Parallel calls make the distinction sharper: elapsed response time follows the path that holds up completion, not the sum of every child span. The useful question is where the response was blocked and what independent measurement can distinguish the candidate causes.

## A slow order, investigated without a shortcut

Consider a **wholly hypothetical** `POST /orders` request through an API gateway, an authentication service, and an order service. The order service reads a database and asks an external inventory partner to reserve stock. Suppose the gateway's 95th-percentile latency for this route rises from an illustrative 300 milliseconds to 2.4 seconds while the success rate remains steady. One retained slow trace shows a 35-millisecond authentication call, a 70-millisecond database query, and a 1.8-second span labeled `reserve inventory`. These figures describe an example, not measurements from a production system. The trace identifies a boundary worth examining; it does not prove that the partner spent 1.8 seconds processing the request.

The engineer first checks whether the slow requests share a deployment, instance, region, or partner operation, and whether the trace is representative of the affected population. A single trace cannot establish the 95th percentile or the frequency of retries. Route-level latency and retry counters establish scope; per-instance connection-pool occupancy and acquisition time test for local contention. Structured order-service logs, correlated by trace ID and span ID where available, can show whether the request attempted the reservation twice and why the first attempt ended. The [OpenTelemetry log data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/) provides fields for those identifiers, but applications still have to emit useful events at the right points.

Suppose those logs show a timeout followed by a retry. That observation narrows the sequence, but several explanations remain: the first call waited for a local connection, packets were delayed in transit, the partner processed slowly, or the partner completed the reservation and its response was lost. To separate them, the team needs timers around pool acquisition and each network attempt, partner-side records keyed to the same logical reservation when available, and a comparison of affected and unaffected instances. If the partner has no corresponding records, a statement about its internal processing time would be speculation. A retry may also make the final HTTP status look healthy while increasing load and latency. The mitigation must be judged against both customer outcomes and downstream attempt rates.

The instrumentation itself now becomes part of the investigation. If the `reserve inventory` span wraps pool acquisition and both attempts, it has collapsed distinct mechanisms into one interval. Adding spans or measurements at those boundaries on a subsequent deployment can distinguish them; retrospectively, the missing measurement cannot be reconstructed from the existing trace. This is why an incident review should record unanswered questions as instrumentation requirements rather than assign a confident cause to the longest colored bar.

## OpenTelemetry standardizes the evidence pipeline

OpenTelemetry supplies APIs, SDKs, semantic conventions, and propagators for producing and correlating telemetry. Its Collector can receive, process, and export signals through configurable pipelines. It is not itself a trace database or visualization interface; those are backend choices. The [Collector documentation](https://opentelemetry.io/docs/collector/) describes this separation. Standardization reduces the amount of bespoke plumbing, but it does not decide which business operation deserves a span, which attribute is safe to retain, or which wait interval needs its own timer.

Automatic instrumentation can cover common HTTP, RPC, and database libraries quickly. It may miss custom clients, connection-pool waits, retry loops, batch jobs, and queue transitions that matter most in a particular system. Manual instrumentation is useful when it marks an operationally meaningful boundary, but every span and attribute consumes application and pipeline resources. Before adopting an instrumentation package, engineers should verify its actual coverage, propagation behavior across asynchronous code, attribute defaults, and interaction with existing logging. The [OpenTelemetry instrumentation guide](https://opentelemetry.io/docs/concepts/instrumentation/) distinguishes automatic and manual approaches.

The telemetry path has its own failure modes. A Collector exporter can buffer data when a backend is unavailable, but a full queue, exhausted retry window, or process crash without persistent storage can lose records. Collector queue depth and failed-export counters therefore need monitoring, particularly during an incident when traffic and error volume may rise together. The [Collector resiliency guide](https://opentelemetry.io/docs/collector/resiliency/) documents these conditions. A trace that disappears precisely during overload is not evidence that the affected request did not exist.

## The cost of asking every question

Metric dimensions are useful only when the resulting series remain manageable. In systems such as Prometheus, every distinct combination of label values creates another time series. Putting an order ID, user ID, or raw URL into a metric label can multiply storage and query work with each request; [Prometheus's naming guidance](https://prometheus.io/docs/practices/naming/) explicitly cautions against unbounded labels. A parameterized route, region, and outcome class can support aggregate comparisons. A particular order identifier belongs in a controlled log or trace record if the investigation genuinely needs it and privacy rules permit it.

Tracing all requests avoids sampling gaps but raises CPU, network, backend indexing, and retention costs. Head sampling decides near the start and saves resources early; it cannot know that an otherwise ordinary request will later time out. Tail sampling can retain traces with errors or long latency after seeing their spans, but it must buffer data and, at scale, route spans of the same trace to a sampling decision point. It cannot recover spans discarded upstream or never emitted. OpenTelemetry's [sampling guidance](https://opentelemetry.io/docs/concepts/sampling/) and [Collector scaling guidance](https://opentelemetry.io/docs/collector/scaling/) make these trade-offs explicit. A sampling policy should match the failure being investigated: a broad, low-rate sample can describe common paths while missing a rare failure mode.

Collection also creates an exposure surface. Request bodies, tokens, and personal identifiers can pass through SDKs, Collectors, storage, and external vendors if captured as attributes or logs. Filtering at the Collector helps but may occur after the data has already crossed a boundary; omitting sensitive fields at the source is stronger. Retention should reflect how long incidents need to remain investigable as well as the cost and sensitivity of each signal. [OpenTelemetry's sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/) assigns those decisions to the implementer. More alerts carry a separate cost: paging on every internal fluctuation consumes attention without clarifying customer impact. User-facing symptoms should drive urgent alerts; detailed internal telemetry should support diagnosis.

An effective design begins with the decisions an on-call engineer must make. Which requests are affected? Where did their time go? Which measurements would distinguish local queueing from remote processing? Those questions justify route-level latency distributions, trace context at service and queue boundaries, structured retry events, and selected timers inside clients. Teams can then choose sampling and retention budgets against the likelihood and cost of missing a rare incident, and test the pipeline by inducing known failures. The goal is not maximum collection; it is enough trustworthy evidence to reject competing explanations.

Distributed systems remain difficult to diagnose because telemetry records what instruments were placed to see, while incidents often turn on behavior between those instruments. Metrics reveal the population, traces reconstruct an observed path, and logs expose local decisions. Diagnosis becomes credible only when engineers can say what each signal proves, where it is incomplete, and what new measurement would resolve the remaining uncertainty.
