## 1. Introdução

Um thread dump é uma observação pontual das pilhas e dos estados de execução de uma JVM. Ele pode apoiar a análise de deadlocks, contenção e períodos de baixa resposta, mas uma captura isolada raramente demonstra causalidade. O problema examinado é como incorporar a coleta ao fluxo operacional de uma aplicação HotSpot sem depender de uma sessão manual com `jcmd` ou `jstack`.

Este trabalho delimita o contrato da API `HotSpotDiagnosticMXBean.dumpThreads`, apresenta uma integração mínima e define critérios para comparar cobertura, custo e risco operacional. O método está disponível desde o JDK 21 [1]. O escopo é diagnóstico; a API não substitui profiling contínuo nem confirma, sozinha, a causa de um incidente.

## 2. Fundamentação e trabalhos relacionados

O MXBean de diagnóstico é registrado no servidor de MBeans da plataforma e pode ser acessado localmente ou por JMX remoto, conforme a configuração da JVM [1]. `ThreadDumpFormat` define `TEXT_PLAIN` e `JSON` [2]. A documentação exige um caminho absoluto para **um arquivo que ainda não existe**; quando a invocação é remota, o caminho se refere ao sistema de arquivos da JVM alvo [1].

O comando `jcmd <pid> Thread.print` produz um dump sob demanda a partir de uma ferramenta externa [3]. `ThreadMXBean.dumpAllThreads` retorna objetos `ThreadInfo` para threads de plataforma e permite consultar informação de monitores e sincronizadores, conforme o suporte da JVM [4]. Essas interfaces têm contratos diferentes: a primeira grava arquivo, a segunda expõe objetos em memória, e `jcmd` atua como ferramenta operacional externa.

## 3. Metodologia e arquitetura de coleta

O trecho abaixo explicita a pré-condição do arquivo. Ele deve ser executado em uma JVM HotSpot compatível; exceções devem ser tratadas pela aplicação chamadora.

```java
import com.sun.management.HotSpotDiagnosticMXBean;
import java.io.IOException;
import java.lang.management.ManagementFactory;
import java.nio.file.Files;
import java.nio.file.Path;

public final class ThreadDumpCapture {
    public static void capture(Path target) throws IOException {
        if (!target.isAbsolute() || Files.exists(target)) {
            throw new IllegalArgumentException("Use um caminho absoluto para um arquivo inexistente");
        }
        HotSpotDiagnosticMXBean bean =
            ManagementFactory.getPlatformMXBean(HotSpotDiagnosticMXBean.class);
        if (bean == null) {
            throw new UnsupportedOperationException("MXBean indisponível nesta JVM");
        }
        bean.dumpThreads(target.toString(), HotSpotDiagnosticMXBean.ThreadDumpFormat.JSON);
    }
}
```

A aplicação deve criar previamente o diretório de destino com permissões restritas, limitar quem pode solicitar a captura e estabelecer quotas de frequência e retenção. Em um endpoint administrativo, autenticação, autorização e trilha de auditoria são requisitos de projeto; expor o MXBean ou o arquivo sem esses controles amplia a superfície de ataque. O nome do arquivo deve ser exclusivo por captura para satisfazer o contrato da API.

O plano de avaliação reproduz três cenários: aplicação ociosa, contenção deliberada de lock e carga com threads virtuais. Para cada cenário, capturar `TEXT_PLAIN` e `JSON`, registrar JDK/JVM, número de threads, tamanho do arquivo, tempo de coleta e impacto na latência das requisições. ## 4. Avaliação e análise de trade-offs

| Mecanismo | Acionamento | Saída | Limite relevante |
| --- | --- | --- | --- |
| `dumpThreads` | Código ou JMX autorizado | Arquivo texto/JSON | Caminho absoluto e arquivo inexistente; suporte dependente da JVM [1, 2] |
| `jcmd Thread.print` | Ferramenta externa com acesso ao processo | Texto | Exige acesso operacional ao processo alvo [3] |
| `ThreadMXBean.dumpAllThreads` | Código/JMX | `ThreadInfo[]` | Contrato documentado para threads de plataforma [4] |

A API de arquivo garante a inclusão das threads de plataforma e **pode** incluir parte ou todas as threads virtuais [1]. Logo, a presença de JSON não deve ser confundida com cobertura total. O custo de CPU, a pausa observável, a quantidade de dados sensíveis e o crescimento do armazenamento variam com a carga e devem ser medidos. Nenhum valor quantitativo é reivindicado aqui.

## 5. Limitações e ameaças à validade

O método pertence ao módulo específico `jdk.management`, não a todas as implementações de Java SE. A implementação padrão da interface pode lançar `UnsupportedOperationException` [1]. A documentação de formato e os campos JSON devem ser verificados para a versão em uso antes de integrar um parser de produção. Um dump representa apenas o instante da captura, pode omitir threads virtuais e pode conter segredos em nomes, pilhas ou contexto operacional. Capturas repetidas, correlacionadas com métricas e eventos, são necessárias para inferências mais robustas.

O exemplo não foi submetido a testes de carga, execução remota ou validação em múltiplos provedores. Diretórios inexistentes, ausência de espaço, corrida entre a verificação e a criação do arquivo e falta de permissão devem ser tratados como falhas esperadas.

## 6. Conclusão e trabalho futuro

`dumpThreads` oferece uma interface programática para capturas de texto ou JSON no HotSpot, com requisitos explícitos de destino e limitações de cobertura. A adoção operacional depende de controle de acesso, política de retenção e testes sob carga. Trabalho futuro deve medir custo por volume de threads, comparar os formatos e validar a cobertura de threads virtuais em versões concretas do JDK.
