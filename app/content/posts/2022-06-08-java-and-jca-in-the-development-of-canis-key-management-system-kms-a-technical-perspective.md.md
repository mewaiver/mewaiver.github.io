In the CANIS repository, a 2026 change prevents the server from silently creating a fresh key database when its existing database is missing. That failure mode matters: a service that appears healthy with an empty store cannot recover the keys on which previously encrypted files depend. The [change credited to Tiago Souza in the project's Git history](https://github.com/metiago/canis-kms/commit/abe465d) illustrates a point often lost in discussions of cryptographic APIs. Generating and wrapping keys is only part of a key service; preserving the ability to recover them is another engineering problem.

## A service for recovering file keys

CANIS is designed for asynchronous exchange of encrypted files between Java services in an organization-managed environment. A producer obtains a service's public key, generates a fresh AES key, encrypts the file on its own host with AES-GCM, and wraps that AES key with RSA-OAEP. The resulting `CANISHYB1` envelope contains the wrapped key, nonce, ciphertext, and authentication tag. A recipient can fetch the envelope later, send the wrapped key to CANIS, and use the returned AES key to decrypt the file locally. File contents need not pass through the key server. These steps are specified in the [CANISP protocol reference](https://github.com/metiago/canis-kms/blob/master/docs/canisp-protocol.md) and implemented in the [Java client](https://github.com/metiago/canis-kms/tree/master/client).

The [file-envelope change in the Git record](https://github.com/metiago/canis-kms/commit/b93bf17) credits Souza with implementing this client-side path. Dividing the work is more than an algorithm choice: RSA protects a small file key, AES handles the file's bytes, and the server's private key need not travel to the producer or recipient. The trade-off is that the unwrapped AES key *does* return to an authenticated client. A compromised admitted client can therefore recover file keys. CANIS's [threat model](https://github.com/metiago/canis-kms/blob/master/docs/threat-model.md) explicitly limits the intended deployment to a shared trust domain.

## What Java's cryptographic architecture contributes

The Java Cryptography Architecture (JCA) supplies provider-backed APIs for key generation, ciphers, randomness, signatures, and key storage. It gives CANIS standard interfaces rather than requiring the project to implement RSA or AES itself. In the [server source](https://github.com/metiago/canis-kms/tree/master/server/src/main/java/io/canis), `KeyPairGenerator` creates 2,048-bit RSA pairs; `Cipher` applies RSA-OAEP with SHA-256 and MGF1 to wrapped keys; and `Cipher` with `AES/GCM/NoPadding` protects the key database. The client uses the same families of primitives to produce and open file envelopes. Oracle's [JCA reference guide](https://docs.oracle.com/en/java/javase/21/security/java-cryptography-architecture-jca-reference-guide.html) explains the provider model and these APIs.

AES-GCM is an authenticated encryption mode: its tag lets decryption reject modified ciphertext when the key and nonce are correct. An ordinary SHA-256 digest alone would not provide the same protection against an active attacker. ECDSA is a signature scheme rather than an encryption algorithm; the file-key wrapping described by the CANIS implementation uses RSA-OAEP. The code does use a `Signature` operation when validating stored RSA key pairs, but file exchange does not rely on digital signatures.

The repository credits Souza with [adding TLS 1.3 mutual authentication to the client](https://github.com/metiago/canis-kms/commit/ae629e0). The current protocol uses client certificates and a subsequent application login. Java Secure Socket Extension (JSSE) handles TLS using Java's security infrastructure; JCA ciphers do not, by themselves, authenticate a remote application. [CANISP](https://github.com/metiago/canis-kms/blob/master/docs/canisp-protocol.md) defines line-oriented commands and typed responses over that connection, including public-key retrieval and the server-side `decrypt` request. The official client is the intended application interface; the wire protocol is an internal contract.

## The database is not a `KeyStore`

CANIS does not keep service private keys in JCA's `KeyStore`. The current implementation uses a custom, encrypted `db.dat` database for RSA key pairs and metadata. The database is protected with AES-GCM under an externally provisioned master key; `CANIS_SECRET_KEY` points to the key file. Java `KeyStore` is used separately for PKCS#12 TLS identity and trust material. A `.dat` extension is only a filename convention, not a security property. The [master-key guide](https://github.com/metiago/canis-kms/blob/master/docs/master-key.md) describes the required file ownership, access controls, and startup checks.

The Git history shows the operational problem being addressed in stages. Changes credited to Souza [added checks on the master-key file](https://github.com/metiago/canis-kms/commit/c597c26) and [prevented silent database recreation](https://github.com/metiago/canis-kms/commit/abe465d). In the current design, a missing or rejected master key stops startup; normal startup also rejects a missing database. These choices make certain failures visible before clients depend on an unusable service. They do not recover lost material. Backups must preserve the database and its matching key under separate controls, with a tested restore procedure, as the project's [recovery runbook](https://github.com/metiago/canis-kms/blob/master/docs/operational-recovery.md) explains. A privileged operator or compromised host that can read both files or process memory remains inside the project's trusted computing base.

## The decisive boundary is authorization

CANIS authenticates clients, but its documented authorization model does not isolate keys by service name or client identity. Any admitted client can request operations involving any stored service key, including decryption and deletion. Names organize keys; they are not access-control policies. For a group of applications already trusted to share one key namespace, that may be an acceptable simplification. For mutually untrusted teams or tenants, it is a material limitation; the project's own [threat model](https://github.com/metiago/canis-kms/blob/master/docs/threat-model.md) recommends separate deployments when independent authorization domains are required.

Key lifecycle also needs deliberate planning. Creating a pair under an existing name is rejected rather than silently replacing it. Rotation therefore calls for a new name and a plan to re-encrypt any envelopes that must remain readable before the old key is removed. Deletion cannot erase copies in backups, snapshots, or JVM memory. These are system properties that no choice of JCA provider can solve on its own.

The reviewed repository supports analysis of Souza's code and its documented security boundary. It does not establish production adoption, measured performance, an independent security audit, or the significance of CANIS beyond its own development record. Those questions require evidence from users, reviewers, or deployments; neither a code commit nor a project citation file can answer them.

CANIS illustrates that key locality and key authority are separate design decisions. Souza's implementation keeps RSA private keys on the server, limiting their distribution. Its shared-access policy still lets every admitted client invoke decryption under every stored service key. Java makes the cryptographic operations available; the service's authorization model determines who can use them.
