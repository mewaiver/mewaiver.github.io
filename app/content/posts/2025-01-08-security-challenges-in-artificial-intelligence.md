An order API begins missing its latency target, but its success rate is unchanged. The gateway's chart shows the slowdown. The authentication service and database report ordinary response times. A worker trace shows a fast call to an external fraud provider. None of these observations explains the extra second the customer waited. This is a **hypothetical incident**, not a report from a production system. Its difficulty lies in a common engineering mistake: treating a collection of accurate measurements as a complete account of a request.

One customer action can cross processes, queues, network links, and organizations. Each records time at boundaries chosen by its owner, often with different clocks and retention rules. A successful response may hide retries; an apparently idle service may have requests waiting before its handler runs. The diagnostic problem is therefore causal: which operation delayed which other operation, and what evidence would separate that explanation from its competitors?

## An alarm establishes impact, not cause

Monitoring is effective at detecting conditions a team decided to measure in advance: route latency, error rates, traffic, and resource saturation. Observability is the ability to investigate behavior after the question changes, using enough internal evidence to distinguish plausible causes. The terms describe purposes rather than separate product categories. Google's [SRE guidance on monitoring distributed systems](https://sre.google/sre-book/monitoring-distributed-systems/) makes the distinction between user-visible symptoms and intermediate causes explicit. A dashboard can establish that an order route is slow; a red panel for the order service does not establish why.

The first diagnostic step is to define the affected population. Is latency elevated across all routes or only order creation? Does the tail worsen in one region, deployment version, or request class? A histogram and request counters can answer those questions without storing every request. A single average can conceal a small group of very slow orders; a single trace cannot tell how common that group is. Metrics make comparisons across populations economical, but aggregation discards the individual sequence that produced each measurement.

Logs preserve local decisions: a job was published, a retry was scheduled, a connection was refused, or a worker rejected an expired request. They are useful when events are structured and carry stable correlation identifiers. Timestamp proximity alone is weak evidence in a busy service, and a log saying “sent” may mean the application handed data to a client library rather than that another system received it. Traces connect instrumented operations across a request, but cannot explain an interval no instrumentation captured. These signals complement one another because each loses different information.

## A trace records relationships, not a complete history

A distributed trace groups spans that represent recorded operations. Each span has a trace ID, its own span ID, start and end timestamps, and, where applicable, a parent span ID. A gateway span can be the parent of an order-service call; the order service can create child spans for a database query and a downstream request. The parent relationship identifies the instrumented causal path. Duration helps locate where time was observed, but duration alone does not explain what happened during it. The [OpenTelemetry trace data model](https://opentelemetry.io/docs/specs/otel/trace/data-model/) also permits span links for relationships, such as message processing, that do not fit a simple parent-child chain.

For that structure to cross a service boundary, the caller must propagate context and the receiver must extract it before starting its span. HTTP instrumentation commonly uses the W3C [Trace Context](https://www.w3.org/TR/trace-context/) `traceparent` header. A queue needs equivalent context in message metadata, and asynchronous code must keep the active context when execution moves between tasks. OpenTelemetry's [messaging conventions](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/), currently marked as in development, use links as the general way to relate a consumer's work to a message's creation context; a single-message consumer may use a parent relationship. If the producer omits that context, a worker can produce a perfectly valid trace that looks unrelated to the order that caused it.

Recording and propagation are separate. A service can forward context without exporting its own span. It can also export a local span while failing to pass context onward. Sampling, filtering, exporter failure, and partial queries can remove spans from the view. As the [trace data model](https://opentelemetry.io/docs/specs/otel/trace/data-model/) notes, even a trace with no visibly missing parent is not proof that every expected child was recorded. A blank stretch may be an unmeasured wait, an uninstrumented operation, or missing telemetry. It is not evidence that the application did no work.

Span timing requires similar care. Sibling operations can overlap, so adding their durations overstates customer-visible latency. A client span may include local connection acquisition and retries as well as remote processing, depending on where its instrumentation begins and ends. Across processes, clock skew can even make a child appear to start before its parent. Use IDs and links to reconstruct relationships; use local timers and independent measurements to attribute the time within a disputed interval.

## An order delayed between services

Consider a **wholly hypothetical** order flow. A request passes through an API gateway and authentication service to an order service. The order service writes to a database, publishes a fraud-check message, and waits for a worker's result. That worker calls an external provider. Suppose the gateway's 95th-percentile latency for order creation rises from an illustrative 300 milliseconds to 1.6 seconds after a deployment, while the success rate remains stable. The example's figures are invented for analysis; they are not a benchmark or field observation.

The engineer first verifies that the rise affects this route and checks request rate, deployment version, region, and error and retry counters. That establishes scope, not causation. Retained slow order traces show brief authentication and database spans, followed by a long span waiting for the fraud-check result. A separate worker trace shows a short provider call. The wait between publishing the message and receiving its result appears to dominate the order's latency. Calling it “provider latency” would be unjustified: the worker's provider span is short, and the missing time may precede the worker entirely. Calling it “broker latency” would also be premature because the worker could have received the message but waited for a local execution slot.

The next evidence must separate those possibilities. The team compares broker message-age and queue-depth metrics, where available, with publish and consumption rates, then checks worker concurrency, pending work, and the time from message receipt to handler start. A correlation ID in both producer and consumer logs can identify the same logical job while tracing context is repaired. However, subtracting timestamps from unsynchronized application hosts is not a reliable way to measure a one-second wait. A broker-observed queue age and a local timer for worker scheduling provide stronger evidence for their respective intervals. Provider-side timings, if available, test whether remote processing also changed; the provider's claim of normal latency covers only requests it actually saw.

Suppose, still hypothetically, broker-side message age and worker backlog rise together, worker throughput falls after the deployment, and provider-side processing times remain steady. The evidence then locates most of the delay **before** the provider call. It does not yet identify why throughput fell. A reduced worker concurrency limit, a thread pool blocked on another task, or a new mix of expensive messages could all produce that pattern. Comparing affected and unaffected worker versions and measuring handler occupancy can narrow it. A controlled rollback under comparable traffic, followed by falling message age and restored throughput, would strengthen the case for the deployment change; it would not make the original trace alone a root-cause proof.

This investigation also changes what the team should instrument. A producer span around publishing and a worker span around processing do not necessarily measure time resident in the queue. A message-age metric and a stable message correlation mechanism expose that boundary. Those choices answer a specific operational question without creating a span for every internal instruction. They also leave a clear residual uncertainty when broker or provider records are unavailable.

## OpenTelemetry standardizes transport, not judgment

OpenTelemetry provides APIs and SDKs to create telemetry, instrumentation libraries for common frameworks, propagators for context, and semantic conventions for consistent names and attributes. Its Collector can receive, process, and export signals to a chosen destination. Storage, search, and visualization come from the backend; OpenTelemetry is not itself an incident diagnosis engine or a trace database. The project's [component documentation](https://opentelemetry.io/docs/concepts/components/) describes those roles.

Automatic instrumentation is a practical starting point for HTTP and database boundaries. It may not know that a fraud-check message is required before an order can complete, or where a custom worker waits for capacity. Manual spans and measurements are worthwhile when they distinguish causes that would lead to different mitigations. Before rollout, engineers should verify library coverage, propagation through proxies and queues, attribute consistency across services, and the behavior of SDK and Collector exporters under load. A Collector queue can fill or an export can fail during the same incident that makes traces most valuable; [OpenTelemetry's resiliency guidance](https://opentelemetry.io/docs/collector/resiliency/) documents those loss modes. Collector health and dropped-data counters belong in the evidence review.

## Visibility has a budget and a security boundary

More telemetry can make diagnosis worse when it expands cost without improving discrimination. In a metric system such as Prometheus, every distinct combination of label values creates a time series. A request or customer ID as a label can produce an effectively unbounded number of series; [Prometheus's naming guidance](https://prometheus.io/docs/practices/naming/) warns against such dimensions. Bounded labels such as route template, operation, and outcome support population comparisons. An individual identifier may belong in a controlled log or trace when necessary to investigate a specific request, with access restrictions and retention chosen for that purpose.

Trace sampling is another explicit trade-off. Head sampling decides early and reduces work before the request finishes; it can discard the rare request that later becomes slow. Tail sampling can retain traces selected by latency or failure, but must hold spans while deciding and bring a trace's spans to a decision point. It cannot recover spans discarded upstream or never emitted. OpenTelemetry's [sampling guidance](https://opentelemetry.io/docs/concepts/sampling/) and [Collector scaling guidance](https://opentelemetry.io/docs/collector/scaling/) describe those costs. A useful policy tests what kinds of failures disappear under the chosen sample rate, rather than assuming that a neat trace view represents the full traffic population.

Instrumentation adds CPU, memory, network, and backend storage work, often when the application is already under stress. Retention sufficient for a later investigation increases storage cost and the period during which sensitive data can be exposed. Request bodies, tokens, and personal identifiers should not enter telemetry by default; filtering after export cannot undo exposure at an earlier stage. [OpenTelemetry's sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/) places field selection, filtering, access, and retention within the system's design. Alert volume has a human cost as well: paging on every internal queue fluctuation can obscure the customer-facing symptom that warrants immediate action. Google's SRE guidance favors actionable symptom-based paging, with deeper internal signals available for investigation.

The choice is not between instrumenting everything and accepting blindness. Teams can begin with service-level latency distributions and error rates, preserve context at meaningful boundaries, and add measurements for waits that would change an operational decision. They can test the evidence path with known failures: delay the worker, drop propagation at a queue, and throttle the telemetry backend. The result is a map of what the system can establish, what it merely suggests, and what it cannot currently see.

Distributed systems remain difficult to diagnose with metrics, logs, and traces because the decisive fact is often a relationship or interval the instruments never recorded. Reliable diagnosis comes from treating telemetry as evidence with a coverage boundary: establish the affected population, reconstruct the recorded path, then measure the gap that separates competing explanations. The most valuable new signal is often not another dashboard panel, but one carefully placed observation that can falsify the wrong story.
